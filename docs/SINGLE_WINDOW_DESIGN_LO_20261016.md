# LVSP: ແຜນ Single Window, ພາສີ ແລະ ຂະບວນການການຄ້າ

ວັນທີ 16 ຕຸລາ 2026. ຂໍ້ກຳນົດຂະບວນການມາຈາກຜູ້ໃຊ້; ເງື່ອນໄຂນິຕິກຳ, ລາຍການເອກະສານ ແລະ ຜູ້ມີອຳນາດຕ້ອງກວດກັບ SOP/ນິຕິກຳທີ່ໃຊ້ຈິງ.

## ສະຖານະທີ່ກວດພົບ

ໂຄງການເດີມມີພື້ນຖານຕັ້ງແຕ່ migration 000860: trade.annual_plan_service_type, integration.external_system, external_identifier, message_envelope ແລະ v_single_window_readiness. ລາຍການ CUSTOMS ແລະ LNSW ມີສະຖານະ PLANNED/DRAFT, endpoint ວ່າງ ແລະ authentication UNCONFIGURED. ນີ້ແມ່ນການກຽມໂຄງສ້າງ ບໍ່ແມ່ນການເຊື່ອມ Single Window ຈິງ.

ມີ service guides/requirements (000740), workflow/tasks, notifications (000610), outbox/inbox (000080), border/customs reference (000513), e-Cert/verification (000850/000860). ຍັງບໍ່ໄດ້ຢືນຢັນວ່າຂະບວນການບໍລິສັດ–ພະນັກງານ–ຜູ້ອະນຸມັດ–ຂາອອກ–ດ່ານ ເຮັດວຽກຄົບວົງຈອນແລ້ວ. ເອກະສານປະຈຳບໍລິສັດ, ຂໍ້ຍົກເວັ້ນ, ການຈອງແຜນ ແລະ ການອອກເລກຂາອອກຕ້ອງຕໍ່ເຂົ້າໃນ workflow ທີ່ກວດສອບໄດ້.

## ຂະບວນການທີ່ຈະໃຊ້

1. ບໍລິສັດເບິ່ງຄູ່ມືແຕ່ລະວຽກ: ເງື່ອນໄຂ, ລາຍການເອກະສານ, ຂັ້ນຕອນ ແລະ ແບບຟອມສະບັບທີ່ມີຜົນ. ເບິ່ງຄູ່ມືໄດ້ກ່ອນ Login; ຍື່ນຕ້ອງເປັນຜູ້ມີສິດຂອງບໍລິສັດນັ້ນ.
2. ສ້າງ Company Document Vault: ເອກະສານປະຈຳຍື່ນຄັ້ງດຽວ, ມີສະບັບ, hash, ຜູ້ກວດ, ວັນເລີ່ມ/ໝົດອາຍຸ ແລະ ສະຖານະ. ຄຳຮ້ອງອ້າງເຖິງສະບັບທີ່ໃຊ້ ບໍ່ແມ່ນ link ທີ່ປ່ຽນໄປຕາມເອກະສານຫຼ້າສຸດ. ເອກະສານໝົດອາຍຸຕ້ອງຍື່ນສະບັບໃໝ່; ສະບັບເກົ່າຍັງເກັບເປັນຫຼັກຖານ.
3. ວຽກທີ່ກຳນົດໃຫ້ມີແຜນປະຈຳປີ: ຍື່ນແຜນ → ກວດ → ຂໍແກ້ໄຂຖ້າຈຳເປັນ → ຜູ້ມີອຳນາດອະນຸມັດ. ເກັບປີ, ປະເພດວຽກ, ທິດທາງການຄ້າ, ລາຍການ, ຫົວໜ່ວຍ ແລະ ສະບັບແຜນ. ບໍ່ບັງຄັບທຸກວຽກໃຫ້ມີແຜນໂດຍບໍ່ກວດ policy.
4. ຍື່ນຄຳຮ້ອງແຕ່ລະຄັ້ງ: ຂໍ້ມູນສິນຄ້າ/ສັດ, ປະເທດ, ດ່ານ, ເອກະສານປະຈຳບໍລິສັດທີ່ອ້າງອີງ ແລະ ເອກະສານສະເພາະຄັ້ງ. ລະບົບກວດຄົບຖ້ວນ/ອາຍຸ/ແຜນກ່ອນ Submit ແລະ ກວດອີກກ່ອນອະນຸມັດ.
5. Submit ແລ້ວຈຶ່ງສ້າງວຽກໃນຄິວຜູ້ຮັບຜິດຊອບ ແລະ ແຈ້ງເຕືອນໃນລະບົບພ້ອມກັນໃນ transaction. ການຂໍເອກະສານເພີ່ມ/ນັດປຶກສາມີຂໍ້ຄວາມ, ຜູ້ສົ່ງ, ວັນທີ, ຄຳຕອບ ແລະ ປະຫວັດ. ບໍ່ສົ່ງ email/SMS ພາຍນອກຈົນກວ່າຈະຕັ້ງຄ່າຊ່ອງທາງແຈ້ງເຕືອນຢ່າງຖືກຕ້ອງ.
6. ຜູ້ອະນຸມັດຢືນຢັນຜົນກວດ. ອະນຸມັດແລ້ວເປັນ APPROVED_PENDING_DISPATCH; ຂາເຂົ້າ–ຂາອອກກວດ ແລະ ອອກເລກທີ/ວັນທີຂາອອກທີ່ບໍ່ຊ້ຳ. ເອກະສານສຳເລັດຈຶ່ງເປັນ ISSUED/PUBLISHED ພ້ອມ QR ແລະ hash ຂອງສະບັບອອກຈິງ.
7. ດ່ານສະແກນ QR ຫຼື ຄົ້ນຫາເລກເອກະສານຜ່ານບັນຊີດ່ານ. ກວດຜູ້ອອກ, ອາຍຸ, ສະຖານະລະງັບ/ຍົກເລີກ, ສະບັບ ແລະ ຍອດຄົງເຫຼືອກ່ອນບັນທຶກຈຳນວນຈິງ. ຮອງຮັບຜ່ານຫຼາຍຄັ້ງ/ບາງສ່ວນ ແລະ ບໍ່ຕັດຊ້ຳຖ້າ Submit ຊ້ຳ.
8. ຈຳນວນຈິງອັບເດດແຜນ, ຍອດໃບອະນຸຍາດ ແລະ ລາຍງານໃນ transaction ດຽວ. ສຳລັບຢາຕ້ານເຊື້ອ ຈຶ່ງເຊື່ອມຫາ ANIMUSE ພ້ອມ source event ID ເພື່ອກັນນັບຊ້ຳ.

## ການຄວບຄຸມແຜນ ແລະ ຂໍ້ຍົກເວັ້ນ

ຍອດວ່າງສຳລັບອອກໃບອະນຸຍາດ = ຍອດແຜນທີ່ອະນຸມັດ + ຍອດເພີ່ມທີ່ອະນຸມັດ − ຍອດຜ່ານຈິງ − ຍອດຈອງຂອງໃບອະນຸຍາດທີ່ຍັງໃຊ້ໄດ້. ຍອດຈອງບໍ່ແມ່ນຍອດນຳເຂົ້າຈິງ. ຕອນຜ່ານດ່ານແມ່ນຫຼຸດຈອງ ແລະ ເພີ່ມຍອດຈິງ. ໃບອະນຸຍາດໝົດອາຍຸ/ຍົກເລີກໃຫ້ຄືນສະເພາະຍອດຈອງທີ່ຍັງບໍ່ໃຊ້. ການແກ້ຍອດຈິງໃຊ້ reversal ມີເຫດຜົນ ແລະ audit, ບໍ່ລຶບປະຫວັດ.

ຂໍ້ຍົກເວັ້ນອາຍຸເອກະສານ ຫຼື ເກີນແຜນ ຕ້ອງເປັນຄຳຂໍ/ຜົນອະນຸມັດຕ່າງຫາກ ມີບໍລິສັດ, ໜ້າວຽກ, ຄຳຮ້ອງ, ສະບັບ policy, ເຫດຜົນ, ຜູ້ມີອຳນາດ, ເອກະສານອ້າງອີງ ແລະ ຂອບເຂດ/ຈຳນວນ/ອາຍຸ. ບໍ່ມີປຸ່ມຍົກເວັ້ນລວມທັງບໍລິສັດ. ລາຍການທີ່ policy ບໍ່ອະນຸຍາດໃຫ້ຍົກເວັ້ນຍັງຖືກບລັອກ. ແຜນເພີ່ມຈາກຄຳອະນຸມັດໜຶ່ງຕ້ອງບັນທຶກຄັ້ງດຽວດ້ວຍ unique reference.

ຕົວຢ່າງ: ແຜນ 100 kg, ຜ່ານແລ້ວ 20, ຈອງ 50 → ວ່າງ 30. ຂໍຄັ້ງໃໝ່ 40 ຕ້ອງອະນຸມັດເພີ່ມ 10 ກ່ອນ. ຫຼັງຈອງໃໝ່ ຍອດຈອງລວມ 90. ຖ້າຜ່ານຈິງ 25 ຈະເປັນຜ່ານຈິງ 45, ຈອງ 65, ໃບໃໝ່ເຫຼືອ 15. ບໍ່ຕັດ 40 ແລ້ວຕັດ 25 ຊ້ຳອີກ.

## ການເຊື່ອມ Single Window / ພາສີ

ໃຊ້ LVSP ເປັນລະບົບວຽກຂອງກົມ; ໃຊ້ adapter ແປງຂໍ້ມູນທີ່ຕົກລົງກັບ Lao NSW/ພາສີ. ບໍ່ສົມມຸດວ່າ API ຂອງເຂົາເປັນ REST ຫຼື ໃຊ້ JSON ຮູບແບບຂອງເຮົາ.

ກຽມ canonical contract ພາຍໃນໃນ integration/contracts/lvsp-trade-event-v1.schema.json. ມີ message ID, correlation ID, schema version, ເລກອ້າງອີງພາຍໃນ/ພາຍນອກ, ສະບັບເອກະສານ, ລາຍການ/ຈຳນວນ/ຫົວໜ່ວຍ, hash ແລະ event type. ນີ້ຍັງບໍ່ແມ່ນ message ທີ່ WCO ຫຼື LNSW ຮັບຮອງ. ຕ້ອງກວດ schema/format ອີກໃນ adapter ກ່ອນຮັບ–ສົ່ງ.

ແຜນ mapping: WCO Data Model ສະບັບທີ່ຄູ່ເຊື່ອມໃຊ້, HS ພ້ອມສະບັບ, ISO country codes, ຫົວໜ່ວຍ UNECE Recommendation 20, ລະຫັດດ່ານທີ່ຕົກລົງ ແລະ ລະຫັດບໍລິສັດ/ຜູ້ຍື່ນ. ບໍ່ສົມມຸດວ່າລະຫັດດ່ານພາຍໃນກົງກັບ UN/LOCODE.

ບັນທຶກເອກະສານພ້ອມ outbox ໃນ transaction; worker ສົ່ງພາຍຫຼັງ ແລະ retry ດ້ວຍ message ID ເດີມ. ຝັ່ງຮັບກວດລາຍເຊັນ/authentication, schema, ຜູ້ສົ່ງ, timestamp/replay ແລະ inbox uniqueness ກ່ອນປະມວນຜົນ. ແຍກ RECEIVED/VALIDATED/PROCESSED/REJECTED; transport ACK ບໍ່ເທົ່າກັບຜົນອະນຸມັດ. ຜົນອະນຸມັດສັດຕະວະແພດ ແລະ ຜົນກວດປ່ອຍພາສີແຍກອຳນາດກັນ.

ປິດ connector ເປັນຄ່າເລີ່ມຕົ້ນ. ຕ້ອງມີ API/EDI specification, sandbox, credentials, mapping ແລະ ຜົນທົດສອບຮ່ວມກັບຄູ່ເຊື່ອມກ່ອນເປີດ. ບໍ່ສົ່ງຂໍ້ມູນໄປພາສີ/LNSW ໃນຂັ້ນນີ້.

## ລາຍເຊັນ ແລະ QR

Login ແລ້ວກົດອະນຸມັດແມ່ນຫຼັກຖານ electronic approval ໃນ workflow; ບໍ່ໄດ້ໝາຍຄວາມວ່າເປັນລາຍເຊັນ PKI ທີ່ຄູ່ເຊື່ອມຍອມຮັບ. ຕ້ອງກຳນົດຜູ້ມີອຳນາດ, identity assurance, signing profile, ໃບຢັ້ງຢືນ/ກະແຈ, ເວລາລົງນາມ ແລະ ການຖອນລາຍເຊັນຕາມຂໍ້ຕົກລົງຈິງ. ຮູບລາຍເຊັນ ຫຼື QR ຢ່າງດຽວບໍ່ພຽງພໍ.

QR ອ້າງເຖິງສະບັບທີ່ອອກຈິງ ແລະ ກວດສະຖານະປັດຈຸບັນໄດ້. ໜ້າ public ສະແດງສະເພາະຂໍ້ມູນກວດຢືນຢັນທີ່ອະນຸຍາດ; ເອກະສານປະກອບ/ຂໍ້ມູນສ່ວນຕົວໃຊ້ສິດຜູ້ໃຊ້. ການຄົ້ນຫາດ້ວຍເລກໃບອະນຸຍາດສຳລັບດ່ານຕ້ອງ Login ແລະ ມີບັນທຶກການເຂົ້າເບິ່ງ.

## ສ່ວນທີ່ເພີ່ມໃນຮອບນີ້ ແລະ ວຽກທີ່ຍັງເຫຼືອ

ເພີ່ມ core/trade-policy.ts ພ້ອມ tests: ກວດ policy ທີ່ອະນຸມັດ, ເອກະສານຕາມບໍລິສັດ/ຄຳຮ້ອງ, ຂໍ້ຍົກເວັ້ນທີ່ຈຳກັດຂອບເຂດ, ຈຳນວນແຜນແບບ decimal ທີ່ແນ່ນອນ, ການຜ່ານບາງສ່ວນ ແລະ ກັນຕັດຊ້ຳ. ເປັນ primitives ສຳລັບນຳໄປຕໍ່ເຂົ້າໃນ workflow ເດີມ; ຍັງບໍ່ບັງຄັບໃຊ້ກັບຄຳຮ້ອງປັດຈຸບັນ ແລະ ບໍ່ມີການສົ່ງພາຍນອກ. authorityVerified ໃນຕົວທົດສອບຕ້ອງມາຈາກ server ກວດອຳນາດຈິງໃນ workflow, ບໍ່ຮັບຄ່າຢືນຢັນຈາກ client.

ຂັ້ນປະຕິບັດ: ຢືນຢັນ service policy/ແບບຟອມ/ອຳນາດ → ເພີ່ມ document vault/version references ແລະ scoped exception records → ເພີ່ມ reservation/clearance ledger ທີ່ lock ແຖວແຜນ/permit ພ້ອມ unique idempotency keys ໃນ transaction → ຕໍ່ເຂົ້າ UI ແລະ workflow → ທົດສອບ concurrent approvals/partial clearance/reversal → ຈຶ່ງເຊື່ອມ sandbox ຂອງ LNSW/ພາສີ. ຕົວທົດສອບ pure function ບໍ່ໄດ້ພິສູດ database concurrency.
